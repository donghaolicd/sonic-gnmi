# ADO Local Developer Sandbox — Executive Decision Summary

> **Date:** 2026-06-24 | **Author:** Generated by Octane plan workflow | **Audience:** Engineering leadership, architects, cross-team stakeholders | **Status:** Approved (Technical: 90/100, Readability: 91/100)

## What We're Building

Developers on sonic-gnmi currently cannot reproduce CI failures locally without access to Azure DevOps infrastructure, a private container registry, and internal build artifacts. Every debugging cycle requires a full pipeline run, creating friction and slowing incident response. This project delivers a low-footprint local sandbox that lets any developer re-execute the same CI steps — install dependencies, run unit and integration tests, and build Debian packages — entirely on their workstation.

The approach treats the existing Azure DevOps pipeline YAML as the single, unmodified source of truth. A thin Python tool reads the pipeline at runtime, resolves ADO-specific constructs (template includes, conditional logic, variable substitution), stubs the three cloud-only artifact download tasks, and executes the resulting shell steps inside the same `sonic-slave-trixie` Docker image that CI uses. No pipeline logic is duplicated into committed scripts, and no production files are touched.

A developer targeting the integration test job, for example, runs `dev/ado-sandbox integration_tests` and gets the full `setup-test-env → make all → make check_gotest_junit` flow locally with test results collected under `dev/build-out/results/` — an experience that previously required triggering a full ADO pipeline run.

## Architecture at a Glance

```
 dev/ado-sandbox (CLI entrypoint)
          │
  ┌───────┼──────────────────────────┐
  ▼       ▼                          ▼
Loader  Resolver                  Executor
(read-  (template expand,         (docker run
 only   ${{ }}, $(), conditions,  sonic-slave-trixie
 YAML)  → flat step list)         OR bare-host)
  ▲                                    │
  │                                    ▼
azure-pipelines.yml             Task Handlers + Stubs
.azure/templates/*.yml          (DownloadArtifact→cache,
[CANONICAL, NEVER MODIFIED]      Publish→local results)
                ▲
         dev/sandbox.yaml
     (image, repo paths, artifact
      cache, var overrides — only
      local-specific knowledge)
```

- **Data flows one way:** YAML is parsed into memory; nothing is written back to any pipeline file.
- **Execution model:** one container per job (not per step), preserving in-job mutable state exactly as ADO's single-agent model does.
- **Deployment:** dev-only tool under `dev/`; never invoked by the production pipeline; zero CI risk.
- **Dependencies:** Python 3.8+, PyYAML, Docker CLI, and the `sonic-slave-trixie` image (buildable from `sonic-buildimage`).
- **Footprint:** 9 new files, all under `dev/`; zero modifications to production pipeline files or Go source.

## Decisions Made

### Approach & Architecture

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Source of truth for CI steps | ADO YAML files (unmodified, read-only) | Prevents the drift and dual-maintenance burden that caused the prior `scripts/`-extraction approach to be abandoned |
| Tool implementation language | Python (not Go, not shell) | String/tree manipulation maps naturally to Python + PyYAML; keeps the tool off the Go build path; Python already used in repo tests |
| OSS ADO local runner adoption | None adopted as executor | No mature offline equivalent exists: `azp-local-runner` requires a live ADO org; `rodmtl` is a validator only; no `act`-equivalent for ADO exists |
| ADO YAML subset coverage | Implement only constructs used by the four templates; fail-fast on anything else | Spec-complete ADO emulation is a multi-month effort and unjustified for ~4 templates; fail-fast prevents silent divergence |
| Container environment | Reuse `sonic-slave-trixie` from `sonic-buildimage` | The org already maintains the exact CI environment; building a new image would be redundant and divergent |
| Per-job vs. per-step container | One container per job | Preserves in-job state (PATH exports, installed debs) matching ADO's single-agent model |

### ADO Semantics Handling

| Decision | Choice | Rationale |
|----------|--------|-----------|
| `${{ }}` compile-time resolution | Restricted evaluator: literals, dotted/bracket-index access (`parameters.*`, `variables['Build.Reason']`), `eq/ne/and/or/not` | Covers every expression actually present in the four templates; broader coverage not needed |
| `$()` runtime macro substitution | ADO-faithful known-name-only: replace only recognized variable names; leave all other `$(...)` verbatim | Real step bodies contain shell command substitutions (`$(go env GOPATH)`, `$(nproc)`) and nested forms that must not be touched; a fail-fast approach would abort three of the four target jobs |
| `condition:` field handling | Evaluate `always()/succeeded()/failed()` and known-operand expressions; unknown conditions default to `true` with a logged note; never fail-fast | Graceful degradation avoids blocking local runs on cloud-only condition semantics |
| Unsupported structural constructs | Fail-fast with file + line + construct in the error message | Makes the contract explicit; developers know immediately when the resolver needs an update, rather than silently diverging |

### Artifact & Stub Strategy

| Decision | Choice | Rationale |
|----------|--------|-----------|
| `DownloadPipelineArtifact@2` (three tasks, no public URL) | Stub: copy from a developer-configured local artifact cache; precise error with acquisition hint if absent | These artifacts are ADO-internal with no public download URL; stubbing keeps the canonical YAML untouched while giving developers a clear path to populate the cache |
| `publish` / `PublishTestResults@2` / `PublishCodeCoverageResults@2` | Stub: copy referenced files to `dev/build-out/results/`; never contact ADO | Preserves output observability locally without any ADO dependency |
| Local-only configuration | Single `dev/sandbox.yaml` file (image override, repo paths, artifact cache, var overrides) | Isolates all sandbox-specific knowledge from the canonical YAML; the canonical files remain byte-identical |
| Multi-repo checkout | Map `checkout:` steps to pre-existing local sibling directories; no automatic clone in v1 | Avoids implicit network operations; explicit pre-requisite is documented and fast to verify |

## Blocking Items

| Item | Status | Owner |
|------|--------|-------|
| `sonic-slave-trixie` image availability (private ACR, not publicly pullable) | 🟡 In Progress | Developer / platform team — must build from `sonic-buildimage` source or obtain ACR credentials |
| Three ADO-only artifacts (`common-lib`, `sonic-buildimage.vs` wheels, `sonic-swss-common-trixie`) have no public download URL | 🟡 In Progress | Developer — must populate local artifact cache via `az pipelines runs artifact download` (requires ADO access) or build from source |
| Local sibling working copies of `sonic-mgmt-common` and `sonic-swss-common` required for container jobs | 🟢 Ready | Developer — standard checkout; documented in `dev/README.md` |

## Follow-up Design Items

| Item | Priority | Description |
|------|----------|-------------|
| Optional auto-clone of missing sibling repos | Medium | v1 requires pre-existing local copies; a future flag could clone at the correct branch automatically (OQ1) |
| `fetch-artifacts` helper command | Medium | Optional `dev/ado-sandbox fetch-artifacts` subcommand using `az pipelines runs artifact download` when ADO credentials are present, to automate artifact cache population (OQ4) |
| Committed `--dry-run` golden outputs as regression fixtures | Medium | Lock resolver behavior against template changes by committing expected resolved-step snapshots; prevents silent semantic drift (OQ5) |
| `arm64` job reproduction | Low | v1 targets amd64 only; arm64 cross-arch emulation is deferred (OQ2 / NG2) |
| Optional YAML schema validation integration | Low | `rodmtl/ado-pipelines-local-runner` or the ADO VS Code language server could provide static validation of the canonical YAML without execution — useful but out of scope for v1 (OQ3) |
